# Спецификация: полная пересборка `vibe-runbooks` в `vibe-mac`

- Статус: approved — утверждено владельцем 2026-08-02
- Дата: 2026-08-02
- База: `origin/main` (`4bc5da0`)
- Рабочая ветка: `codex/vibe-mac-refactor`
- Исходное требование: «Промпт для Codex: собрать собственный инсталлер `vibe-mac`»
- Поправки A1/A2 из `plan.md`: утверждены владельцем 2026-08-02

## 1. Решение в одном абзаце

Текущий агент-ведомый учебный runbook полностью заменяется автономным,
идемпотентным установщиком macOS. Новый продукт превращает чистый Mac в
минимальное рабочее окружение для AI-ассистированной веб-разработки через одну
команду, умеет безопасно продолжать прерванную установку, проверять результат,
диагностировать типовые проблемы и откатывать только собственные изменения.
Flutter, Xcode.app, Android, Netlify-маршрут и LMS-передача больше не входят в
продукт.

## 2. Источники правды и роль промптов

У проекта будут три разных, не смешиваемых слоя инструкций:

1. Этот документ — каноническая продуктовая спецификация: что строим и по каким
   критериям принимаем.
2. Корневой `AGENTS.md` — короткий рабочий контракт для агентов, которые
   разрабатывают сам `vibe-mac`: ветки, тесты, безопасность, ссылки на эту
   спецификацию и `plan.md`.
3. `config/AGENTS.md` и `config/CLAUDE.md` — шаблоны доктрины для стартового
   проекта. MVP не меняет глобальные правила всех проектов на Mac.

Исходный строительный промпт не копируется буквально в корневой `AGENTS.md`:
одноразовые команды «создай репозиторий с нуля» не должны повторно исполняться в
каждой будущей сессии.

## 3. Проблема текущего продукта

Сейчас репозиторий решает другую задачу:

- Codex вручную ведёт человека по фазам и отдельным `runbook.md`;
- основной маршрут перегружен Flutter/Xcode/Android и отдельным Netlify-треком;
- прогресс в JSON ведёт агент, а не установщик;
- нет единого оркестратора, строгого `verify`, read-only диагностики и
  ownership-aware отката;
- первая победа связана с мобильным приложением или публикацией сайта, а не с
  минимальным локальным рабочим местом.

Смешивать две архитектуры нельзя: старый маршрут удаляется как код и
документация, а полезные безопасные функции переносятся выборочно.

## 4. Целевые пользователи

### 4.1 Основной пользователь

Полный новичок на Mac, который впервые открыл Терминал и хочет начать локальную
AI-ассистированную разработку. Он не выбирает версии, менеджеры пакетов или
варианты PATH. Его действия ограничены следующим:

- вставить одну стартовую команду;
- прочитать короткое объяснение и явно подтвердить системный шаг;
- один раз ввести пароль Mac, если кэш `sudo` позволяет;
- самостоятельно завершить входы в системном браузере;
- запустить первый готовый промпт и открыть HTML-страницу.

### 4.2 Сопровождающий

Владелец проекта или разработчик, который выпускает версию установщика,
обновляет зафиксированные источники инструментов, запускает CI и расследует
логи без доступа к секретам пользователя.

## 5. Пользовательские сценарии

1. На чистом поддерживаемом Mac пользователь запускает одну команду и получает
   готовую среду без технических развилок.
2. После сетевой ошибки или закрытия Терминала повторный запуск продолжает с
   первого незавершённого шага.
3. Повторный успешный запуск ничего не дублирует и быстро сообщает «Уже стоит».
4. `DRY_RUN=1` показывает точный план без записей, сети, `sudo`, GUI и входов.
5. `SKIP_DEFAULTS=1` оставляет настройки macOS без изменений.
6. `EXTRAS=1` добавляет только согласованный дополнительный слой.
7. `verify.sh` показывает понятную таблицу, версии и одну точную команду ремонта
   для каждого непрошедшего пункта.
8. `doctor.sh` диагностирует строго без изменений; `doctor.sh --repair`
   отдельно показывает план ремонта и требует явного подтверждения.
9. `uninstall.sh` по умолчанию только показывает план и никогда не удаляет то,
   что существовало до `vibe-mac`.
10. В `~/dev/hello-vibe` пользователь запускает Claude, вставляет готовый промпт
    и получает однофайловую HTML-страницу, открываемую двойным кликом.

## 6. Поддерживаемая платформа

- Основная и полностью принимаемая платформа: Apple Silicon (`arm64`).
- Intel (`x86_64`): по умолчанию fail-closed до любых записей. Экспериментальный
  best-effort запуск возможен только с `ALLOW_UNSUPPORTED_INTEL=1`, после
  обязательного DRY_RUN и typed-подтверждения `INTEL`; он использует
  архитектурно корректный Homebrew prefix и не входит в обещание поддержки.
- Только macOS; запуск на другой ОС завершается до любых изменений.
- Минимум macOS 14. На более старой версии preflight объясняет ограничение и
  завершает работу без изменений.
- Preflight проверяет свободное место, сеть, доступность официальных источников,
  архитектуру, версию macOS и возможность запросить `sudo`.
- Минимальный порог свободного места фиксируется в `guard.sh` и будет обоснован
  суммой фактических пакетов в плане; предварительное значение — 15 ГБ.

## 9. Оркестрация и состояние

`install.sh` — единственная точка входа и владелец последовательности шагов.

- Каждый шаг имеет стабильный ID и запускается в отдельном процессе Bash.
- Успешный шаг атомарно записывается в progress JSON через временный файл и
  `mv`; повреждённый JSON не считается успешным состоянием.
- Перед пропуском шага повторно проверяется фактический результат, а не только
  маркер состояния.
- При ошибке trap печатает номер шага, понятное описание и путь к логу.
- Продолжение не повторяет завершённые внешние действия и не повторяет входы.
- Версия state-схемы и версия установщика сохраняются рядом с прогрессом.
- Одновременный запуск двух установщиков блокируется lock-файлом.

### 9.1 Контракт shell-кода и интерфейса

- `install.sh`, библиотеки и шаги до установки Homebrew совместимы с системным
  Bash 3.2 чистого Mac. В них нельзя использовать ассоциативные массивы,
  `mapfile`, `${var,,}`, `wait -n` и другие возможности новых Bash.
- Механизм раннего state не зависит от ещё не установленных `jq`, Node, Python
  или GNU-утилит; точный атомарный способ записи выбирается в плане из
  встроенных средств macOS.
- Каждый `.sh` начинается с `#!/usr/bin/env bash` и `set -euo pipefail`.
- Каждый шаг печатает один из стабильных итогов: `Установлено`, `Уже стоит`,
  `Пропущено`, `Ошибка`.
- Весь пользовательский текст — по-русски, на «ты», короткими фразами без
  необъяснённого жаргона.
- Наличие GUI-программы проверяется по точному пути в `/Applications`, а CLI —
  по команде и ожидаемому формату версии; одного progress-маркера недостаточно.
- Все пути проходят проверку и передаются командам в кавычках. `rm -rf` по
  переменной, широкие glob и `eval` над внешними данными запрещены.

## 10. Bootstrap и сетевые источники

Пользовательский UX остаётся однокомандным, но каноническая production-команда
указывает на неизменяемый release tag, а не на mutable `main`.

Форма команды после выпуска версии остаётся одной вставляемой строкой, но
сначала сохраняет bootstrap в точный temp и сверяет literal SHA-256,
опубликованный по доверенному release-каналу:

```bash
VIBE_MAC_SHA256='<SHA256>' /bin/bash -c '<скачать versioned bootstrap в mktemp → сверить literal SHA-256 → запустить локально>'
```

Точная безопасно экранированная команда проектируется в `plan.md` и до
release-гейта остаётся placeholder. Загружаемый файл является только небольшим
bootstrap с зафиксированными версией архива и literal checksum архива.
Bootstrap проверяется до исполнения, а затем сам независимо проверяет архив до
распаковки. SHA bootstrap не скачивается рядом с ним: он уже встроен в
копируемую команду. Release использует signed tag и GitHub immutable release;
mismatch, неизвестный signer или отсутствие immutable-флага блокируют
выполнение. Основной набор скриптов не исполняется из сетевого потока.

Тонкий bootstrap:

1. создаёт временную папку;
2. скачивает архив конкретной версии;
3. проверяет SHA-256 архива, встроенный в уже проверенный bootstrap;
4. распаковывает полный репозиторий с `lib/`, `steps/` и Brewfile в постоянный
   `~/.vibe-mac/releases/<version>/`;
5. атомарно обновляет ссылку `~/.vibe-mac/current` и управляемые launchers в
   `~/.vibe-mac/bin/`;
6. запускает `install.sh` из постоянного versioned bundle;
7. удаляет только собственную download-temp папку через точный trap.

Пользователю остаются стабильные команды:

- `vibe-mac-verify`;
- `vibe-mac-doctor` и `vibe-mac-doctor --repair`;
- `vibe-mac-uninstall`.

Managed PATH для `~/.vibe-mac/bin` добавляется с backup и проверяется до
завершения. Обновление ставит новую версию рядом со старой; предыдущий bundle
не удаляется до успешного `verify`. Uninstall перед удалением текущего bundle
копирует собственный исполняемый контур в точный temp, чтобы не удалить скрипт
из-под выполняющегося процесса.

Команда с `main` может быть документирована только как preview для
разработчиков. Установщики Homebrew, Oh My Zsh и AI-инструментов не исполняются
прямо через `curl | bash`: файл сначала скачивается в точный временный путь,
проверяется по зафиксированному источнику/контрольной сумме и только затем
запускается. Manifest может дублировать метаданные, но не является единственным
trust anchor. Точные официальные способы и версии фиксируются в `plan.md` после
проверки первичных источников.

`retry()` применяется только к безопасным повторяемым загрузкам и проверкам.
Логины, создание внешних ресурсов и другие внешние записи автоматически не
повторяются.

## 11. Привилегии и участие человека

- Установщик запрещено запускать целиком от `root`.
- До первого привилегированного действия пользователь видит точный список,
  зачем нужен `sudo`, и явно подтверждает продолжение.
- Все root-команды группируются в один короткий заранее показанный
  privileged-phase без стороннего скачанного кода между ними. После видимого
  `sudo -v` выполняется только allowlist, затем `sudo -k`; фонового keepalive
  нет. «Пароль один раз» — best effort, а не гарантия.
- Каждая привилегированная команда печатается до запуска и не принимает
  невалидированные пути. Поздняя root-команда требует нового объяснения,
  подтверждения и `sudo -v`.
- Пароль не читается скриптом, не передаётся в аргументах и не попадает в лог.
- Перед браузерным входом установщик объясняет, какой аккаунт нужен, ждёт явное
  подтверждение и отдаёт управление официальному CLI/системному браузеру.
- Перед любым GUI-событием действует общий порядок: объяснить, какое системное
  окно появится и что нажать → дождаться Enter → запустить точную команду →
  дождаться проверяемого результата. Для CLT это отдельное объяснение «это не
  Xcode.app, а около 1 ГБ базовых утилит», затем `xcode-select --install` и
  проверка `xcode-select -p`.
- После установки бинарников интерактивные подпункты последовательно запускают
  официальные входы GitHub, Claude, Codex и Cursor. Для Codex это `codex login`
  с браузерным входом ChatGPT. Если вход отложен или нет TTY, установка остаётся
  технически завершённой, а `verify.sh` печатает один точный ручной шаг.
- Вход не оборачивается в `retry()` и не считается завершённым без проверки
  официальной status-командой, когда такая команда доступна.
- Автоматического создания репозитория, push, публикации, оплаты или деплоя нет.

## 12. Файлы пользователя, конфигурация и резервные копии

- Перед первой записью в пользовательский файл создаётся backup в
  `~/.vibe-mac-backup/<timestamp>/` с правами только владельца.
- Конфигурация добавляется managed-блоками с уникальными маркерами; повторный
  запуск обновляет блок, а не дублирует строки.
- Существующие `~/.zshrc` и конфиги Ghostty/Starship не перезаписываются
  целиком. Глобальные `~/.claude/CLAUDE.md` и `~/.codex/AGENTS.md` не меняются.
- Manifest хранит исходный хэш, backup, применённый managed-блок и признак
  `preexisting` для каждого пакета/файла/default.
- Если пользователь изменил файл после установки, uninstall не восстанавливает
  его молча, а показывает конфликт и оставляет backup.
- Runtime-каталоги, state, manifest, backup и логи создаются с `umask 077`.
- Для прямых preexisting Homebrew formula/cask запрещены явные upgrade,
  reinstall, relink и cleanup; Brewfile применяется с `--no-upgrade`. Homebrew
  остаётся rolling package manager и при установке нового обязательного пакета
  может изменить требуемую транзитивную зависимость. Такие dependency-delta
  нельзя скрывать: они фиксируются снимками до/после, пишутся в manifest и
  отдельно показываются пользователю. Formula/cask из Brewfile являются
  плавающими версиями, а не lockfile; точные версии фактической установки
  сохраняются в manifest и release evidence.
- Git global defaults задаются только для отсутствующих ключей. `user.name` и
  `user.email` никогда не угадываются и не перезаписываются.
- `mise` устанавливает нужные версии, но не меняет существующие global defaults.
  На чистом Mac defaults создаются и записываются в manifest; стартовый проект
  всегда получает собственный `.mise.toml` с точными Node/Python версиями.

## 13. Логи и секреты

- Лог: `~/.vibe-mac/logs/install-<timestamp>.log`, права `0600`.
- Логи содержат шаги, статусы, версии и ошибки, но не полный дамп окружения,
  содержимое credential-файлов, токены, cookies, пароли или ответы OAuth.
- Auth-команды выполняются вне полного stdout/stderr-трассирования.
- Установщик не читает `~/.ssh`, `~/.aws`, `~/.azure`, `~/.kube` и не создаёт
  `.env` с секретами.
- Доктрина агентов запрещает просить или записывать секреты в чат, код, Git,
  `.env`, config и переменные окружения; для проектов adarasoft допустим только
  Azure Key Vault, а без одобренного хранилища агент обязан остановиться.
- OAuth-credentials хранит только официальный CLI своим штатным способом;
  установщик их не читает, не логирует, не копирует и не включает в backup.
- Доктрина также запрещает передавать PII/PHI сторонним LLM, использовать
  `--no-verify`, `git add -A`, force-push и прямую работу в `main`/`master`.

## 14. `verify.sh`

Проверка ничего не устанавливает и печатает таблицу из 12 агрегированных
критериев:

1. Xcode Command Line Tools;
2. Homebrew;
3. Git + GitHub CLI;
4. Ghostty;
5. zsh + Oh My Zsh + Starship + шрифт;
6. современный CLI-набор;
7. mise и его shell activation;
8. Node.js LTS;
9. Python 3.12;
10. uv;
11. Claude + Codex + Cursor/Cursor Agent;
12. `~/dev/hello-vibe` и применённая доктрина агента.

Каждая красная строка содержит ровно одну repair-команду. Внизу выводятся
`N из 12 готово` и отдельные ручные статусы входа: GitHub, Claude, Codex,
Cursor. Отсутствующий вход не маскируется, но не смешивается с установкой
бинарника.

Exit code:

- `0` — все обязательные технические критерии готовы;
- `1` — есть непрошедшие обязательные критерии;
- `2` — сама проверка не смогла корректно выполниться.

## 15. `doctor.sh`

Без флагов doctor строго read-only и проверяет:

- Homebrew prefix и PATH;
- managed-блоки Homebrew/mise/Starship в shell-конфигурации;
- исполняемые файлы и конфликтующие версии;
- права только на точные каталоги, которыми должен владеть пользователь;
- целостность state/manifest/backup-ссылок.

`doctor.sh --repair` сначала печатает детальный план и требует явное
подтверждение. Он может восстановить только управляемые PATH-блоки и точечно
исправить доказанную проблему прав. Рекурсивный `chown`, переустановка всего
стека и скрытый `sudo` запрещены.

## 16. `uninstall.sh`

- По умолчанию работает как dry-run.
- Применение требует флаг `--apply`, показа точных целей и отдельного явного
  подтверждения.
- Удаляются только пакеты/managed-блоки, которые manifest пометил как созданные
  `vibe-mac`; preexisting-компоненты не удаляются.
- Xcode CLT и Homebrew автоматически не удаляются: для них выводится только
  отдельная официальная ручная инструкция.
- `~/dev/hello-vibe`, пользовательские Git-репозитории, аккаунты, credentials и
  backup-каталоги автоматически не удаляются.
- Широкие glob, `rm -rf` по переменной и удаление вне allowlist запрещены.
- Изменённые после установки файлы остаются на месте с понятным сообщением о
  конфликте.

## 17. Первая победа

`90-workspace.sh` безопасно создаёт `~/dev/hello-vibe`, если такой путь ещё не
занят:

- `index.html` с минимальной стартовой страницей;
- локальный Git-репозиторий с рабочей веткой, но без remote, push и публикации;
- проектные `AGENTS.md` и `CLAUDE.md`;
- текст первого промпта для Claude: создать или улучшить одну HTML-страницу в
  одном файле, не трогая остальные файлы и не публикуя результат;
- понятную команду открытия страницы в системном браузере.

Если каталог уже существует, содержимое не перезаписывается. Целевой UX —
увидеть локальный результат в первые 15 минут на типичной сети; это продуктовая
цель, а не причина скрывать ошибки или пропускать проверки.

## 18. macOS defaults

Без `SKIP_DEFAULTS=1` MVP меняет только обратимые и явно перечисленные настройки:

- Dock: автоскрытие;
- Finder: показывать расширения файлов.

Исходные значения пишутся в manifest и могут быть восстановлены. Hot corners не
меняются в MVP, потому что исходный промпт не определяет конкретные действия для
углов; их добавление требует отдельного продуктового решения.

## 19. Тестовая стратегия

Тесты не устанавливают реальный софт и не меняют настоящий HOME.

- Bats запускается с синтетическими `HOME`, `PATH`, brew/mise/git/gh/curl/sudo
  stubs и временным state.
- Unit-тесты: UI, `have`, PATH marker, retry/backoff, backup, manifest,
  atomic JSON, arch/macOS/disk guards, redaction, lock.
- Оркестрация: порядок шагов, resume после сбоя, повторный запуск, stop-on-error.
- Негативные проверки: DRY_RUN гарантированно падает тестом при любой записи,
  сети, `sudo`, GUI или browser open; тест сначала демонстрирует красный
  результат на заведомо плохой реализации.
- Bootstrap: checksum mismatch, частичный/битый архив, tar path traversal,
  symlink escape и ошибка распаковки завершаются до исполнения основного кода;
  unknown signer/изменённый tag тоже блокируются; cleanup затрагивает только
  созданный процессом точный temp-каталог.
- Brewfile: точный обязательный/extra-набор и отсутствие запрещённого стека.
- Preexisting contract: прямые уже установленные пакеты и существующие
  Git/mise global-настройки после sandbox install семантически не изменяются;
  отдельно проверяется классификация и отчёт для неизбежной транзитивной
  Homebrew dependency-delta.
- Конфиги: managed-блок не дублируется, существующее содержимое сохраняется.
- Doctrine contract: шаблоны содержат полный запрет секретов/PII, Key Vault
  правило и Git approval-гейты; глобальные agent-файлы остаются byte-for-byte.
- Verify: все три exit code, версии, repair hint для каждого критерия; каждый
  компонент агрегата проверяется отдельным негативным кейсом. Tripwire запрещает
  запись, сеть, `sudo` и `open`.
- Doctor: default zero-write подтверждается тем же tripwire; repair требует
  approval и меняет только allowlist.
- Uninstall: сквозной сценарий baseline → fake install → пользовательская
  правка → apply; corrupt/missing manifest, абсолютный/`..` путь, symlink escape,
  подменённый backup и preexisting package завершаются fail-closed.
- Network policy: integration-тест доказывает, что обычные загрузки проходят
  только через wrapper с тремя попытками и тестовым backoff без реального sleep,
  а auth/external writes никогда автоматически не повторяются.
- Redaction: canary-пароль, token и OAuth-ответ не появляются ни в обычном, ни
  в error-логе.
- Human/GUI contract: event-trace подтверждает порядок
  `объяснение → подтверждение → команда → проверка`; без подтверждения GUI,
  browser и password-команда не вызываются.
- Fault injection: отдельный сбой на каждом шаге `00`–`90`; success marker
  появляется только после фактической проверки, упавший шаг повторяется, ранее
  успешные внешние действия — нет.
- Второй полный sandbox-прогон сравнивает не только файлы, но и trace всех
  mutating/network/sudo-команд: новых backup, managed-блоков и state churn нет.
- Workspace: существующий каталог не перезаписывается; новый создаётся без
  remote/push/deploy.
- CI: `bash -n`, ShellCheck, Bats на Ubuntu; все entrypoint запускаются также
  через `/bin/bash`; отдельный read-only smoke выполняется на macOS runner.

Числа тестов в отчёте всегда привязываются к SHA проверенной базы.

## 20. Критерии приёмки

Рефакторинг принимается, когда одновременно выполнено следующее:

1. Старый фазовый маршрут и запрещённые установочные шаги отсутствуют.
2. Структура соответствует разделу 8; все shell-файлы используют
   `#!/usr/bin/env bash` и `set -euo pipefail`.
3. Pre-Homebrew код проходит совместимость с Bash 3.2 и не требует ещё не
   установленных runtime/CLI.
4. Локальный fixture bootstrap с version/checksum использует тот же оркестратор;
   доступность публичного tag URL проверяется только на release-гейте.
5. `DRY_RUN=1` доказан тестами как zero-write/no-network/no-sudo/no-GUI.
6. Два последовательных sandbox-прогона дают одинаковый результат без дублей.
7. Прерывание после каждого слоя можно продолжить по state без повторения
   завершённых действий.
8. Все пользовательские правки имеют backup и manifest ownership.
9. `verify.sh` реализует 12 критериев, точные repair hints и корректные exit
   codes.
10. `doctor.sh` read-only по умолчанию; repair отделён и ограничен allowlist.
11. `uninstall.sh` dry-run по умолчанию и не удаляет preexisting/изменённые
    данные.
12. macOS smoke проходит preflight и DRY_RUN без внешних изменений; ветки
    `arm64`/Intel покрыты unit-тестами, а реальный Apple Silicon — release-гейтом.
13. ShellCheck, `bash -n` и весь Bats-набор зелёные на одном commit SHA.
14. Secret scan diff не находит ключей, токенов, паролей и строк подключения.
15. README на русском содержит точный состав, время, шаблон versioned quick
    start с пометкой «после релиза», флаги, ручные входы, диагностику, откат и
    границы поддержки.
16. Независимое read-only ревью не находит blocker/high проблем.
17. Прямые preexisting пакеты, Git/mise global config и глобальные агентские
    инструкции доказанно не изменяются; любая транзитивная Homebrew
    dependency-delta полностью зафиксирована и показана отдельно.

### 20.1 Отдельный release-гейт

Этот гейт не блокирует кодовый PR, но обязателен до публикации production-команды:

1. создан неизменяемый version tag/release и опубликованы архив с checksum;
2. bootstrap скачан по публичному URL, проверен literal SHA до исполнения и
   затем проверил архив по встроенному checksum; tag signed, release immutable;
3. на одноразовом чистом Apple Silicon Mac/VM с macOS 14+ выполнены полный install,
   интерактивные входы, `verify.sh`, повторный идемпотентный install,
   `doctor.sh` и dry-run uninstall;
4. версия, commit SHA, macOS, итог `12/12`, длительность и ручные шаги записаны
   в release evidence без секретов;
5. только после этого README получает готовую production-команду без
   placeholder.

## 21. Миграция из текущего репозитория

- Работа выполняется in-place с сохранением Git-истории в отдельной ветке и PR.
- Старые tracked-файлы удаляются только как обратимый Git diff.
- Никакие уже установленные на машине Flutter/Xcode/Android/Netlify, глобальные
  хуки или каталоги `~/vibecoding` автоматически не удаляются.
- Полезные реализации детекта архитектуры, идемпотентного PATH, human pauses и
  Bats-подхода можно перенести после проверки, но старые названия фаз и их
  маршрутизация не сохраняются.
- Переименование GitHub-репозитория/remote, выпуск релиза, merge и публикация
  bootstrap-команды не входят в этот PR и требуют отдельного явного решения.

## 22. Вне scope этой итерации

- переименование или создание GitHub-репозитория;
- merge в `main`, релиз и публичная публикация установщика;
- деплой приложений или сайтов;
- автоматическая регистрация/авторизация аккаунтов;
- сбор и передача телеметрии;
- перенос существующих пользовательских проектов;
- удаление старых мобильных/веб-инструментов с Mac;
- backend, базы данных, Azure-инфраструктура и LMS;
- настройка hot corners;
- полноценная гарантия поддержки Intel.

## 23. Явно принимаемые проектные решения

Утверждение этой спецификации означает согласие со следующими трактовками
исходного промпта:

1. Текущий репозиторий пересобирается in-place и сохраняет историю.
2. Исходный промпт становится этой канонической спецификацией, а не буквальным
   бесконечно исполняемым `AGENTS.md`.
3. Production bootstrap привязан к неизменяемой версии и checksum; `main` не
   является канонической командой новичка.
4. Используется системный zsh, без второй Homebrew-копии.
5. Runtime state живёт в `~/.vibe-mac`, а не в Git checkout.
6. Doctor по умолчанию только диагностирует; ремонт — отдельный режим.
7. В MVP доктрина устанавливается только в стартовый проект; глобальные файлы
   агентов не меняются.
8. Hot corners отложены до отдельного точного решения.
9. GitHub rename/release/publish выполняются после этого PR отдельными
   approval-гейтами.

После утверждения документа следующий гейт — `plan.md`: точная файловая карта,
содержимое обоих Brewfile, официальные источники/версии, порядок реализации и
команды проверки. До отдельного утверждения `plan.md` код не меняется.
